# Consuming cs2-kit via Conan {#conan_guide}

[TOC]

The kit and its SDK dependencies are published as Conan packages, so a plugin
project needs no submodules: `conan install` delivers prebuilt `libcs2-kit`,
the HL2SDK headers and prebuilt Valve libs, Metamod headers, generated
protobuf headers, and the `cs2_add_plugin` CMake API.

The packages live on a **private** Cloudsmith remote - Valve's Source SDK
license does not permit public redistribution, so nothing here goes to Conan
Center. Ask a maintainer for a read entitlement token.

## Packages

| Package | Contents |
|---------|----------|
| `cs2-kit/x.y.z` | prebuilt static lib, public headers, generated `.pb.h`, `cmake/` helpers, gamedata, plugin template. Option `with_postgres` gates the Database module (pulls libpqxx). |
| `hl2sdk-cs2/<yyyy.mm.dd>` | trimmed HL2SDK mirror-layout tree: headers, prebuilt Valve libs, protoc, the source-only TUs `cs2_add_plugin` compiles per plugin. Versioned by the upstream commit date. |
| `metamod-source/2.0.0.<yyyymmdd>` | Metamod core + SourceHook headers (header-only). |

Third-party dependencies (cpr, nlohmann_json, libpqxx, openssl, ...) are
uploaded alongside, built with the canonical profiles - consumers compile
nothing.

## Setup

```sh
# Canonical profiles (linux-steamrt, windows-msvc) installed by name:
conan config install https://github.com/voltygg/cs2-kit.git -sf conan

# The private remote:
conan remote add voltygg https://conan.cloudsmith.io/voltygg/cs2-kit/
conan remote login voltygg <user> -p <entitlement-token>
```

The profiles are required, not a convenience: the Linux binaries are built
with gcc-14 against the old libstdc++ ABI (`_GLIBCXX_USE_CXX11_ABI=0`, what
the Valve prebuilt libs use) and the Windows binaries with the static MSVC
runtime. The kit's `validate()` rejects mismatching profiles with a pointer
back here.

## Scaffold a project

With any cs2-kit checkout (only the scripts are needed, no submodules):

```sh
mkdir my-plugins && cd my-plugins
python <cs2-kit>/scripts/init_project.py --conan --plugin my-plugin
```

Then follow the generated README: `conan install` + `cmake --workflow`. The
project's CMakeLists is `find_package(cs2-kit CONFIG REQUIRED)` plus one
`add_subdirectory(plugins/<name>)` per plugin; each plugin's CMakeLists is
one `cs2_add_plugin(<name>)` call.

## How the CMake side works

`find_package(cs2-kit)` (generated by CMakeDeps) links `CS2Kit::CS2Kit` with
`CS2Kit::HL2SDK` and `CS2Kit::Metamod` behind it, and includes the kit's
shipped `cmake/CS2Plugin.cmake` / `cmake/CS2Tests.cmake` as build modules -
that is where `cs2_add_plugin` and `cs2_add_tests` come from. The hl2sdk
package ships a build module of its own that points `CS2KIT_HL2SDK_DIR` at
its package folder, which is how the per-plugin `convar.cpp`/`memoverride.cpp`
TUs resolve; the package tree mirrors the upstream SDK layout, so the same
CMake works in submodule mode and package mode.

## Publishing (maintainers)

`.github/workflows/publish-conan.yml` in this repo:

- **cs2-kit** publishes on every `v*` tag (Release + Debug, with and without
  postgres, Linux + Windows), version taken from the tag.
- **SDK packages** publish only via manual dispatch (`publish_sdks: true`).
  To move the pins: update the `vendor/` submodules, `recipes/*/conandata.yml`,
  and the version constants in `conanfile.py` in one PR, then dispatch.
- Requires the `CLOUDSMITH_API_KEY` secret (write token). A `smoke` job then
  consumes the published kit on a clean runner with `--build=never`.

Local equivalent (any platform):

```sh
conan create recipes/metamod-source --version 2.0.0.<yyyymmdd> -pr:a <profile> -s build_type=Release
conan create recipes/hl2sdk-cs2 --version <yyyy.mm.dd> -pr:a <profile> -s build_type=Release
# --lockfile="": conan.lock pins the vendored-dev graph, not the SDK packages.
conan create . -pr:a <profile> -s build_type=Release --build=missing --lockfile=""
conan upload "*" -r voltygg --confirm
```

## Mode detection

The kit's own `conanfile.py` serves both worlds: with the `vendor/` submodules
checked out (this repo, or the cs2-plugins monorepo) it behaves as the
plain consumer conanfile `build.py` always used; exported via `conan create`
(which omits `vendor/`) it becomes the package recipe and requires the SDK
packages instead. Nothing to configure.
